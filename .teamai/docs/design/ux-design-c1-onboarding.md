## 一、C.1 Onboarding 对话流程设计

### 设计原则

基于 TASTE 框架的核心认知：
- **不问抽象问题** - 避免："你喜欢什么风格？"、"你偏向简洁还是详细？"
- **情境化提取** - 让用户描述具体情境，系统隐性抽取品味线索
- **自然对话感** - 让用户感觉是在互相了解，而不是在做"设置"

### 对话示例设计（2-3 轮）

#### 示例 1：开发导向型用户

**系统引导语：**
```
让我们互相了解一下——这样可以让我更好地配合你的工作节奏
```

---

**第 1 轮对话：**

系统: `来聊聊你最近在做的项目吧？`

用户响应 1A（技术细节型）:
> 我在做一个 Next.js 的 API 服务，用 TypeScript 处理各种业务逻辑，现在在重构数据层……

**隐性提取：**
- `domain: web-development/typescript/api`
- `task_type: refactoring/data-layer`
- `communication_style: direct-western`（直接陈述）
- `discourse_system: technical`（技术术语多）

用户响应 1B（问题导向型）:
> 客户那边总是在改需求，代码改来改去，我现在在想怎么让改动不那么痛苦……

**隐性提取：**
- `domain: software-consulting/client-work`
- `risk_level: medium`（变更频繁带来风险）
- `value_orientation: relationship-first`（关注客户体验）
- `sensitivity: requirements-changes`（对需求变更敏感）

---

**第 2 轮对话：**

系统: `听起来这确实是个挑战。你觉得什么样的结果让你觉得"这就对了"？`

用户响应 2A（稳定感型）:
> 代码能跑、不会出 bug，改动一处不会影响另一处

**隐性提取：**
- `taste_standard.stable: positive_vibes = ["可预测的变更", "低耦合"]`
- `intervention_threshold: high`（需要稳定的产出）

用户响应 2B（敏捷感型）:
> 快速响应需求变化，哪怕偶尔有 bug，先把功能给客户用了再说

**隐性提取：**
- `taste_standard.agile: positive_vibes = ["快速迭代", "先发制人"]`
- `intervention_threshold: low`（容忍不确定性）

用户响应 2C（审美型）:
> 代码干净、结构清晰，我自己看起来也舒服

**隐性提取：**
- `taste_standard.clean: positive_vibes = ["简洁结构", "可读性"]`
- `depth_preference: high`（在乎代码审美）

---

**第 3 轮对话（可选）：**

系统: `嗯，如果我在帮你做某件事，你觉得什么情况下你肯定会接手自己做？`

用户响应 3A（核心决策型）:
> 涉及数据库 schema 变更的时候，那必须我来

**隐性提取：**
- `symbiosis_boundary.reserved: ["database-schema-changes"]`
- `control_level: high`（保留核心控制权）

用户响应 3B（质量把关型）:
> 如果影响到线上的稳定性，我肯定会亲自检查一遍

**隐性提取：**
- `contextual_triggers: ["production-stability-risk"]`
- `trust_level: medium`（需要验证关键操作）

---

#### 示例 2：非技术协作型用户

**第 1 轮：**

系统: `能不能说说你平时主要解决什么类型的问题？`

用户: `我会写一些脚本帮我处理表格数据，有时候还要把不同系统的数据导过来导过去...`

**隐性提取：**
- `domain: productivity/data-automation`
- `user_type: non-developer/light-coder`
- `communication_style: indirect-eastern`（描述性而非技术性）

---

**第 2 轮：**

系统: `上次有让你觉得"这就很顺手"的例子吗？`

用户: `就是一次我那个表格脚本，我改了一个地方，然后其他地方自动就对了，不用我一个个改`

**隐性提取：**
- `taste_standard.automation: positive_vibes = ["一次改、多处生效"]`
- `discourse_system: humanities`（用感受而非技术词汇）

---

#### 示例 3：混合型用户（开发 + 设计）

**第 1 轮：**

系统: `来聊聊你现在手头在忙的事？`

用户: `有两个方向，一边在给产品做交互设计稿，另一边还要写点前端代码把效果实现出来...`

**隐性提取：**
- `experience_topology: ["ux-design", "frontend-development"]`
- `discourse_system: mixed`（既懂设计也懂技术）

---

**第 2 轮：**

系统: `感觉两边都要照顾？那你觉得什么样的产出让你觉得"可以了"？`

用户: `设计稿好看是基础，但更要考虑能不能落地实现；代码写出来也要考虑UI效果，不能只是功能对了`

**隐性提取：**
- `taste_standard.bridge: positive_vibes = ["可实现的创意", "有审美的代码"]`
- `value_orientation: balanced`（兼顾多重要求）

---

### TASTE.md 四维度隐性提取映射

| 对话线索 | 隐性提取维度 | 示例触发词 |
|---------|-------------|-----------|
| 提到的技术栈/业务类型 | **Experience Topology** | "API服务"、"Next.js"、"客户需求" |
| 描述"对的/错的"感受 | **Taste Standards** | "这就对了"、"舒服"、"麻烦" |
| 描述什么时候会干预 | **Tension Position** | "必须我来"、"我来检查一遍" |
| 描述信任/不信任的任务类型 | **Symbiosis Boundary** | "数据库schema"、"线上稳定性" |

## 二、项目创建 Skill（Phase 1.5）Taste 隐形采集

### 用户感知 vs 系统采集的分裂设计

| 维度 | 用户感知 | 系统采集（隐形） |
|-----|---------|----------------|
| **入口** | "创建新项目" | Skill 启动 |
| **流程名称** | "项目创建访谈" | TASTE 采集器 |
| **可见步骤** | 1.项目背景 → 2.核心目标 → 3.确认创建 | Project TASTE + Ontology |
| **显式内容** | 项目信息、目标、协作模式 | 用户回答中的品味线索 |
| **界面表现** | 标准表单/向导流程 | 对话式引导 × 结构化采集 |

### 访谈流程设计（3 个关键问题 + 1 个确认）

#### 第 1 步：项目背景 → 隐性提取 Experience Topology

**用户可能的回答（3 类）：**

> 给电商网站做库存管理，用 Java 写 API，前端用 React，数据存在 PostgreSQL 上，还要接第三方物流 API...

**隐性提取：**

```json
  "task_type": "backend-integration",
  "environment": "java-react-postgres-stack",
  "discourse_system": "technical"

```

B. 业务目标型:
> 我们要做一个能实时追踪库存的系统，让仓管人员能快速查询、也能自动预警缺货...

**隐性提取：**
```json
"context_features": {
  "domain": "ecommerce/inventory-management",
  "task_type": "warehousing-optimization",
  "user_type": "business-focused",
  "discourse_system": "business"
```

C. 问题导向型:
> 现在的库存系统太慢了，每次查都要等半天，还经常报错，老板让我重做...

**隐性提取：**
```json

  "domain": "ecommerce/inventory-management",
  "risk_level": "high",
  "value_orientation": "efficiency-first",
```

### 自然融入 Taste 的对话式追问

当用户在访谈中某些回答触发了品味线索时，系统会用自然追问进一步隐性采集：

**示例：**

用户在第 1 步回答：
> 这个项目是做一个金融风控系统，数据流比较复杂，涉及到实时计算...

系统追问（自然对话，用户感觉不到是在"设置品味"）：
> 听起来数据量不小？如果数据量突然变大，你希望系统怎么处理？
    ○ 优先保证精度，慢点也行
    ○ 优先快速响应，精度可以降低
    ○ 两者都要，我自己来调参数

**隐性提取：**
- 选择 1: `taste_standard.precision-first: positive_vibes = ["accuracy"]`, `intervention_threshold: high`
- 选择 2: `taste_standard.speed-first: positive_vibes = ["latency"]`, `risk_tolerance: high`
- 选择 3: `symbiosis_boundary.reserved: ["performance-tuning"]`, `control_level: high`

## 三、C.2-C.3 渐进式揭示策略

### 设计哲学：自然演进，而非功能突现

| 阶段 | 用户感知 | 何时出现 | 感觉来源 |
|-----|---------|---------|---------|
| **初始** | "这个 AI 助手能帮我完成任务" | 首次使用 | 核心功能可见 |
| **首次介入** | "它在关键时刻问我是否确认" | 第一次执行 risky 操作 | ECO 张力自然显现 |
| **习惯形成** | "它好像懂我的风格了" | 连续 3 次确认同一操作 | 信任学习机制 |
| **渐进揭示** | "原来还能看到它记了什么" | 使用一段时间后（1-2周） | 显式品味收集入口 |
| **高级功能** | "我可以定义哪些任务委托" | 用户主动探索或主动触发 | Power User 模式 |

---

### 具体揭示策略

#### 1. C.2 行动确认的渐进式激活

**首次激活（Week 1 使用）：**
- 用户执行第一 risky 操作（如 `git push --force`）
- 弹窗首次出现：`正在执行强制推送，这将覆盖远程提交... [确认] [取消]`
- 同时底部提示：`📌 你的操作会让我了解你的偏好，更精准地配合你`

**用户不会感觉：** "系统突然增加了新功能"
**用户会感觉：** "这是自然的保护机制"

---

#### 2. C.3 信任学习的自然触发

**触发时机：**
- 用户连续 3 次确认同一类操作（如 `npm install`）
- 系统触发：`我发现你已经多次确认了依赖安装操作，以后我可以自动执行吗？`
  - `✓ 是，自动执行（不再询问）`
  - `✗ 暂时保持询问`

**用户不会感觉：** "功能突然出来了"
**用户会感觉：** "系统记住了我的习惯"

---

#### 3. C.4 显式品味收集的渐进式进入

**Week 1-4：** 完全隐藏按钮

**Week 4 后（累计使用 3+ 次确认操作）：**
- 在设置或个人中心出现低调入口：
  ```
  ┌─────────────────────┐
  │ 偏好设置    [🗑️]   │
  │                   │
  │ 我记了一些你的偏... │
  │ [查看详情]         │
  └─────────────────────┘
  ```

**Week 6 后（用户有主动探索行为，如多次打开不同页面）：**
- 在主界面出现更明显的入口（可选）：
  ```
  ┌─────────────────────────────────────────┐
  │  [我的偏好]  [历史]  [···]            │
  └─────────────────────────────────────────┘
  ```

**Week 8 后（Power User 特征：频繁使用、主动操作）：**
- 提示：`发现您使用频率高，可以定义哪些操作委托给我` → 进入 C.4 Power User 模式

---

### "使用一段时间后"的自然性实现

| 触发条件 | 使用的信号 | 软件工程实现 |
|---------|-----------|-------------|
| 使用了多次 risky 操作 | `action_confirm_log.length >= 3` | 本地事件日志 |
| 有主动探索行为 | `page_navigation_events >= 5` | 前端行为追踪 |
| 连续使用时间 > 1 周 | `session_creation_date < now - 7d` | 会话时间戳 |
| Power User 特征 | `active_days >= 10` 且 `manual_operations >= 5` | 复合指标 |

所有基于用户的真实行为，而非"时间到 + 功能突现"。
