## Context

SENSE.12现有SDK仅声明事件、回复和文件能力，没有办公能力发现与调用端口。用户要求Agent感知IM SDK能力，避免按办公操作逐项扩展Core。完整设计事实源为docs/specs/epic-SENSE/story-SENSE.14/architecture.md。

## Goals / Non-Goals

目标：统一可发现、可授权、可按需调用的连接能力，三平台来源有实证，新增同契约操作无需改Core。
非目标：遍历SDK即可获得完整权限和语义、全量办公产品封装、任意第三方服务接入、自动提权、业务事件订阅、记忆隔离。

## Decisions

1. Plugin SDK增加可选目录／执行接口，描述只含序列化schema与元数据；平台方法映射留在插件。官方工具目录优先；SDK从匹配版本的可信描述生成目录。无描述则标为未支持。反射方法名无法还原运行时已擦除的类型、授权和副作用，因此不选。
2. Agent由feature层注册固定发现／调用工具，经Host注入当前连接能力；schema按需加载。新增操作仅更新平台目录或适配数据，不新增Core日程／待办工具。不全量注入目录。
3. 目录与权限分离：可用集合取平台、当前授权、连接设置和Agent scope交集。未知授权不当作已授权。消息actor不自动成为委托主体；Host持有授权映射，模型不得选择任意凭据、URL或SDK路径。通用工具调用仍做单项风险和既有HITL判断。
4. 描述缓存按连接／主体／授权版本分隔，以DataFile保存于data/perception/capabilities；凭据仍在安全存储。按生命周期和目录变更通知刷新，调用前核对权限和版本，不新增配置页高频轮询。重启恢复代理而非恢复全局当前账号。
5. 调用ID复用已有审计/状态机制；写操作不盲目重试。支持平台幂等则传键，结果不确定则核对或保留待确认态。日志只保留安全类别与诊断关联。
6. 依赖方向保持Desktop/Web → Core features/modules → integrations/shared/storage。工具在features组装，integrations通过注入与通用协议调用，不反向依赖业务模块。Worker只持有代理，不能持有或输出token；插件不得依赖Desktop/Web。
7. 实施先串行完成来源及Core契约；三个插件写入范围分开，Agent/Worker与UI按稳定接口推进，集成最后串行。具体范围见Story implementation.md；遵循本会话用户替换后的规约，不套用旧强制子代理流程。

## Risks / Trade-offs

平台没有可枚举描述或官方工具目录覆盖有限 → P1先证实来源，未支持操作明确展示，不伪造能力或无限承诺。
schema无法表达权限与副作用 → 必需补充可信描述元数据，未知操作不自动开放；不依赖LLM判断授权。
身份混淆及目录注入 → 宿主绑定主体、对目录schema/大小/来源做验证，描述仅作工具数据。
连接撤权与在途写入竞态 → 阻断新调用，尝试取消；外部已完成操作不可承诺撤销。
多个平台验证条件不同 → 支持矩阵逐项标明实证；未验证项不以模拟客户端测试勾选完成。

## Migration Plan

可选SDK扩展兼容旧插件。用户显式开启办公能力后授权并生成目录；安装SDK不自动启用写操作。增加能力缓存不迁移原消息/记忆；回滚关闭能力通路并保留缓存与审计。Desktop包验证新增SDK描述文件及Worker代理，平台CI分别验收。

## Open Questions

P1需落实：各平台默认SDK版本对应的机器描述来源、可用工具服务是否存在、权限是否支持无副作用查询、应用／用户委托的授权方式和幂等能力。SDK、CLI及MCP不能假定等价。来源未落实前不得将该平台办公能力标为可用。测试账号和执行主体在真实调用前绑定；当前规划不触发外部操作。
