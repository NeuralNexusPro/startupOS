# OriginOS Project / Agent / Skill 架构标准 

**版本：** 4.0.0  
**发布日期：** 2026-05-19  
**维护团队：** Archersado

---

## 一、体系总览：Project → Agent → Skill

### 1.1 三层架构

OriginOS 的智能体系由三个核心层级构成：**项目（Project）**、**智能体（Agent）**、**技能（Skill）**。

```
Project（目标 / 语境 / 数据范围）
  └── Agent（身份 / 记忆 / 风格 / 工具授权）
        ├── Skill（原子级能力，按需加载）
        └── System Tools（系统内置工具）
```

| 层级 | 定义 | 职责焦点 |
|------|------|----------|
| **Project** | 一个完整的工作上下文空间，如研究项目、产品线、任务域 | 提供目标、上下文与数据范围 |
| **Agent** | 项目内的智能角色或执行者，具备身份、记忆与风格 | 作为语义中枢，处理任务并调用技能 |
| **Skill** | 可复用的功能单元，由自然语言定义能力逻辑 | 实现原子级行为或判断，服务于 Agent |

### 1.2 层级逻辑

三层结构代表三种问题视角：
- **Project：** 为什么（Why）—— 目标、语境与价值
- **Agent：** 怎么做（How）—— 执行逻辑与风格
- **Skill：** 做什么（What）—— 具体步骤与输出

### 1.3 分层原则

1. 信息仅沿自上而下传递定义（Project 管理 Agent，Agent 组织 Skill）
2. 每层均为可独立阅读的自然语言文档
3. 命名与标识保持可追溯关系：Project > Agent > Skill

## 二、Agent 类型体系

### 2.1 类型分类

OriginOS 定义了三种 Agent 类型，分别服务于不同的工作场景。

| 类型 | 定义 | 特征 | 核心场景 |
|------|------|------|----------|
| **角色型 Agent（Role Agent）** | 具备人格、阶段切换与专业判断的智能体 | 有状态机、多阶段行为、风格一致、可安装/卸载技能 | 架构顾问、编辑导师、业务访谈师 |
| **项目型 Agent（Project Agent）** | 由项目上下文驱动的执行型智能体 | 自动感知项目本体与业务模型、内置工作流、按需加载技能 | 业务建模、项目专属任务执行 |
| **任务型 Agent（Task Agent）** | 专注具体任务的轻量智能体 | 流程化、目标明确、无独立记忆文件 | 系统内置技能执行、首页应用入口 |

### 2.2 Agent 通用文件体系

每个 Agent 由一组自然语言 Markdown 文件定义其行为，全部采用自然语言描述，不包含代码。

| 文件 | 功能 | 角色型 | 项目型 | 任务型 | 标注要点 |
|------|------|--------|--------|--------|----------|
| **Agent.md** | 身份、职责与边界定义 | ✅ | ✅ | ✅ | 用自然语言说明智能体的工作范围 |
| **Role.md** | 状态机与阶段行为 | ✅ | — | — | 描述角色在不同阶段的行为特征与切换条件 |
| **Tool.md** | 工具与技能授权 | ✅ | ✅ | — | 声明允许使用的工具列表与已绑定技能 |
| **Taste.md** | 沟通语气、表达结构与风格偏好 | ✅ | ✅ | — | 明确语气、句式和格式偏好 |
| **Memory.md** | 历史会话摘要与持久记忆 | ✅ | ✅ | — | 系统自动维护，记录关键决策与用户偏好 |
| **Knowledge.md** | 知识库索引快照 | ✅ | ✅ | — | 从对话中提炼的知识索引 |
| **Patterns.md** | 经验模式索引快照 | ✅ | ✅ | — | 从实践中提炼的最佳路径与失败教训 |

## 三、Agent 工程标准

### 3.1 Agent.md 编写标准

Agent.md 是 Agent 的身份定义文件，必须包含元数据声明和自然语言正文。

**元数据声明规范：**

| 字段 | 说明 | 示例 |
|------|------|------|
| agentId | 唯一标识（kebab-case） | oracle-project-interview |
| agentType | 类型标识 | interview |
| version | 版本号 | 1.0.0 |
| name | 显示名称 | Oracle - 项目访谈助手 |

**正文结构：**

| 章节 | 内容 | 推荐字数 |
|------|------|----------|
| 身份 | 我是谁，我在什么项目中工作 | 100–150 |
| 职责 | 我能做什么，我的核心任务是什么 | 150–300 |
| 工作方式 | 我怎么做——流程、原则 | 200–400 |
| 边界 | 我不做什么 | 50–100 |
| 对话风格 | 我如何与用户交流 | 100–200 |
| 引导语 | 首次对话的开场白（访谈类 Agent） | 200–300 |
| 技能指引 | 我拥有的技能列表及何时使用 | 100–200 |

**写作要点：**
- 使用第一人称（"我是..."、"我可以..."）
- 职责部分使用"动词 + 对象"结构（如"检查字段完整性"）
- 边界部分明确"不做什么"，防止越界行为
- 面向用户的对话中不使用技术术语
- 平均 400–600 字，句式自然

**示例：**

```markdown
---
agentId: project-initialization-agent
agentType: interview
version: 1.0.0
name: Oracle - 项目访谈助手
---

# Oracle - 项目访谈助手

## 身份

我是 Oracle，OriginOS 的业务经验访谈师。我的使命是通过结构化对话，
将用户的实际工作经验和业务实践沉淀为基于本体的业务模型。

## 职责

### 核心职责
- 通过对话引导用户复述其亲身经历的业务过程
- 识别用户日常工作中的行业领域和业务概念
- 梳理用户实际操作中的关键业务对象、它们之间的联系和处理规则
- 将用户的具身经验显性化为结构化的业务模型

### 工作方式
- 采用三阶段模式：领域发现 → 业务精炼 → 模型审阅
- 每个阶段由独立 Skill 驱动，按需加载对应 Skill 文件获取详细指导
- 主动提问，引导用户回忆实际工作场景
- 全程使用业务语言，避免技术术语
- 重点关注"你平时是怎么做的"，而非"你想构建什么系统"

## 核心原则

1. **一次一个问题** — 避免同时问多个问题
2. **工具调用优先** — 每次回复前先加载当前阶段的 Skill，严格按指引执行
3. **业务语言** — 面向用户的对话中永远不使用技术术语
4. **增量构建** — 识别到业务元素后立即更新业务模型
```

### 3.2 Role.md 编写标准

Role.md 定义角色的状态机——角色在不同阶段展现不同的行为特征。

**元数据声明规范：**

| 字段 | 说明 | 示例 |
|------|------|------|
| currentPhase | 当前所处阶段 | default |
| phases | 阶段列表（名称、行为特征、进出条件） | 见下方 |
| transitions | 阶段转换规则（从哪到哪、条件） | 见下方 |

**正文规则（When→Then→Outcome 句式）：**

```markdown
### When 用户提交设计草稿
Then 从模块边界与责任分层角度审查架构
Outcome 生成改进建议草案。

### When 用户请求性能优化意见
Then 提示优化方向并要求具体指标
Outcome 输出性能评估要点。

### When 项目阶段结束
Then 总结风险与技术债务
Outcome 更新最佳实践记录。
```

**规则要点：**
- "When" 表触发情境；"Then" 表行为动作；"Outcome" 表可观察结果
- 各条规则独立，不嵌套
- 至少三条，最多七条

**示例（项目访谈 Agent 的 Role.md）：**

```markdown
---
currentPhase: "domain-discovery"
phases:
  - name: "domain-discovery"
    behavior: "通过开放式提问识别用户的行业领域和核心业务概念"
    entryCondition: "项目创建后首次对话"
    exitCondition: "识别出至少 2 个核心业务对象"
  - name: "business-refinement"
    behavior: "深度挖掘每个业务对象的属性、关联、规则和约束"
    entryCondition: "已有核心业务对象，但属性或规则不完整"
    exitCondition: "所有业务对象均有完整属性和规则"
  - name: "model-review"
    behavior: "向用户展示完整业务模型，支持查看、修改和确认"
    entryCondition: "业务模型完整或用户主动要求审阅"
    exitCondition: "用户确认模型或提出新的修改需求"
transitions:
  - from: "domain-discovery"
    to: "business-refinement"
    condition: "识别出至少 2 个核心业务对象"
  - from: "business-refinement"
    to: "model-review"
    condition: "所有业务对象均有完整属性和规则"
  - from: "model-review"
    to: "business-refinement"
    condition: "用户提出修改需求"
---

## 阶段行为规则

### When 进入领域发现阶段
Then 使用引导语开场，通过开放式提问了解用户的日常工作
Outcome 识别出至少 2 个核心业务对象及其初步关系

### When 进入业务精炼阶段
Then 逐一深挖每个业务对象的属性、关联、规则和约束
Outcome 所有业务对象均有完整的属性、关系、规则和生命周期

### When 进入模型审阅阶段
Then 以结构化方式向用户展示完整业务模型
Outcome 用户确认模型或提出修改意见
```

### 3.3 Tool.md 编写标准

Tool.md 声明 Agent 被授权使用的工具和已绑定的技能。

**元数据声明规范：**

| 字段 | 说明 | 示例 |
|------|------|------|
| toolsVersion | 工具版本 | 1.0.0 |
| allowedTools | 允许使用的工具列表 | ["write_file", "read_file", ...] |

**正文结构：**
1. **工具说明** — 逐一描述每个工具的功能和使用场景
2. **工作流技能表** — 列出内置的阶段技能及其触发条件
3. **已安装技能** — 以表格形式列出已安装的技能代码、名称、描述
4. **工具使用原则** — 如"路径始终用相对路径"、"每次操作后保存进度"等

**示例：**

```markdown
---
toolsVersion: 1.0.0
allowedTools: [write_file, read_file, edit_file, list_files, delete_file,
  query_ontology, create_domain, create_concept, search_ontology, get_current_time]
---

# 可用工具

本 Agent 可以使用以下内置工具完成访谈任务。

## 文件工具

### write_file
写入内容到文件（完整覆盖，目录不存在时自动创建）

**使用场景**: 保存访谈进度、写入或更新业务模型

### read_file
读取文件内容

**使用场景**: 读取已有访谈记录、加载业务模型、加载技能文件

## 工作流技能

访谈工作流内置三个阶段技能，**无需安装，按需加载**：

| 阶段 | 触发条件 | 说明 |
|------|----------|------|
| 领域发现 | 业务模型不存在或为空 | 从用户日常工作中识别行业领域和核心业务概念 |
| 业务精炼 | 业务模型存在但不完整 | 深度挖掘实体属性、关系和规则 |
| 模型审阅 | 业务模型完整或用户要求 | 展示当前模型，支持查看、修改和确认 |

## 工具使用原则

1. **路径始终用相对路径** — 系统自动解析，无需手动指定
2. **每次操作后保存进度** — 及时更新进度文件
3. **重要操作先确认** — 删除文件前向用户确认
4. **技能优先** — 先读取对应阶段的 Skill 文件，严格按其指引执行
```

### 3.4 Taste.md 编写标准

Taste.md 定义 Agent 的沟通风格，追求"好"的系统性表达。

**正文结构：**

| 章节 | 内容 |
|------|------|
| 核心理念 | 关于"好"的追求——不仅是功能正确，而是令人愉悦的体验 |
| 表达风格 | 语言风格（简洁有力、具体而非抽象、人性化、主动而非被动） |
| 回复节奏 | 短问短答、不必要时不使用复杂格式 |
| 思考品质 | 洞察力、简洁性、优雅性、实用性 |
| 协作风格 | 与用户的关系（像聪明的同事，不像服务员） |
| 交付标准 | 交付物要"刚好够"，不多不少 |
| 领域特有品味 | 针对具体业务领域的品味要求 |

**示例：**

```markdown
---
fileType: taste
version: 1.0.0
name: 品味工程
---

# 品味工程

## 核心理念

品味工程是关于「好」的系统性追求——不仅是功能正确，
而是令人愉悦、优雅、有温度的体验。

## 表达风格

### 语言风格
- **简洁有力** — 去掉废话，每句话都有重量
- **具体而非抽象** — 用具体例子代替模糊概念
- **人性化** — 有温度、有个性，不像机器说话
- **主动而非被动** — "我来做"而非"这可以被做"

### 回复节奏
- 短问短答，长问深答
- 不必要时不使用复杂格式

## 协作风格

### 与用户的关系
- 像聪明的同事，不像服务员
- 直接表达判断，有依据时据理力争
- 承认不确定，不假装无所不知

## 业务建模品味
- 实体命名要贴近业务语言，不要技术黑话
- 关系要反映真实业务意图，不是数据结构
- 规则要捕捉业务智慧，不是简单约束

## 对话品味
- 访谈问题要引发思考，不是收集数据
- 每个问题背后要有洞察目标
- 总结要让用户感到"被理解"
```

### 3.5 Memory.md 编写标准

Memory.md 是 Agent 的持久记忆，记录从对话中提炼的关键信息。

**结构：**

```markdown
## 关键决策

- [决策描述，记录为何如此选择]
- ...

## 用户偏好

- [用户的工作风格偏好]
- ...

## 更新记忆

- [从对话中提炼的新事实]
- ...
```

**维护规则：**
- 系统自动维护，Agent 不手动编辑
- 每轮对话的要点自动记录
- 定期由自动记忆整理机制处理：去重、去除过时条目、提炼原子级事实
- 面向用户可见，但不由用户直接编辑

## 四、认知系统架构

### 4.1 三个核心组件

认知系统让 Agent 在服务用户过程中积累知识、沉淀经验、持续进化。

| 组件 | 职责 | 说明 |
|------|------|------|
| **知识库（Knowledge Base）** | 理解世界 — 领域知识、事实、概念的结构化存储 | 通过对话自动提取，索引到 Knowledge.md |
| **实践日志（Practice Log）** | 记录行为 — Agent 决策、工具选择、执行结果的日志 | 每轮对话自动记录，支持回溯分析 |
| **经验模式库（Pattern Library）** | 优化行为 — 从实践中提炼的最佳路径、反模式 | 定期从实践日志中分析提炼，索引到 Patterns.md |

### 4.2 触发时机

| 触发时机 | 操作 | 重量级 |
|----------|------|--------|
| 每轮对话结束 | 记录实践日志到文件系统 | 轻量（只写磁盘） |
| 会话结束 | 批量分析日志 → 提取知识 + 沉淀模式 | 重量（LLM 分析） |
| 每 N 轮（可选） | 增量分析最近未处理的日志 | 重量（LLM 分析） |
| Agent 启动 | 加载 Knowledge.md + Patterns.md 快照到提示词 | 轻量（读文件） |

### 4.3 Memory 系统

Agent 拥有三层记忆架构：

| 层级 | 载体 | 更新频率 | 说明 |
|------|------|----------|------|
| **运行记忆** | 对话消息历史 | 每轮自动 | LLM 的短期上下文窗口 |
| **持久记忆** | Memory.md | session_end / consolidation | 仅保留长期稳定认知，由 memory-core consolidation 统一整理 |
| **历史存储** | 结构化日志记录文件 | 每轮追加写入 | 支持增量读取和回溯分析 |

**长期记忆整理（memory-core consolidation）：**
- 运行时 turn 数据先进入 recall/history，而不是直接写入 `Memory.md`
- 会话结束或周期性 consolidation 时，再将稳定偏好、长期约束、事实与反思分流沉淀
- `Dream` 仅保留为兼容壳，不再作为默认运行时记忆整理机制

## 五、Skill 工程标准

### 5.1 Skill 概述

**Skill** 是最小的可复用任务单元，它通过自然语言定义一段能力：输入、处理与输出。所有技能均以目录形式存在，主文件为 `SKILL.md`。

Skill 的描述应像写"说明书"，确保任何人阅读后即可理解输入要求与产出内容。

### 5.2 技能来源分类

| 来源 | 说明 | 安装方式 |
|------|------|----------|
| **系统内置** | OriginOS 系统预装的核心技能（如业务精炼、领域发现） | 随系统发布，无需安装 |
| **项目专属** | 项目自定义的技能，存放在项目目录中 | 创建项目时自动配置 |
| **用户安装** | 从技能市场安装的第三方技能 | 通过技能管理安装到 Agent 的技能目录 |

### 5.3 SKILL.md 基础结构

**元数据声明规范：**

| 字段 | 说明 | 示例 |
|------|------|------|
| name | 显示名称 | 文档校对助手 |
| code | 唯一标识（kebab-case） | doc-proofreader |
| description | 一句话描述功能 | 审查文本拼写、格式和一致性 |
| version | 版本号 | 1.0.0 |
| type | 技能类型 | SIMPLE / COMPLEX / WORKFLOW |
| author | 作者 | OriginOS 团队 |
| tags | 标签列表 | [skill, language] |
| reads | 输入数据类型 | [text] |
| writes | 输出数据类型 | [report] |

**正文结构：**

| 章节 | 内容要求 | 推荐字数 |
|------|---------|----------|
| **功能说明** | 介绍技能解决的问题与目的 | 100–150 |
| **触发场景** | 说明何时、何种情境下使用 | 80–120 |
| **执行步骤** | 按步骤列出逻辑或工作过程 | ≤200 |
| **数据契约（I/O）** | 描述输入输出语义关系，使用表格化表达 | 图表化 |
| **注意事项** | 限制与边界说明，简明列点 | 简明 |

### 5.4 完整 Skill 示例

```markdown
---
name: 订单验证器
code: order-checker
description: 校验订单数据结构并生成报告。
version: 1.0.0
type: SIMPLE
author: OriginOS 团队
tags: [skill, ontology]
reads: [order]
writes: [validation]
---

# 订单验证器

## 功能说明
验证订单字段完整性与数值逻辑，输出结构化校验报告。

## 触发场景
当新订单创建或订单更新时激活。

## 执行步骤
1. 读取订单字段定义；
```

### 5.5 本体 I/O 契约（Ontology I/O Contract）

**目标：** 在语义层定义技能与结构化数据的交互范围。

**定义：**
- **输入契约（Input Contract）：** 技能从系统读取哪些语义对象与字段
- **输出契约（Output Contract）：** 技能写入或生成哪些语义结果

**书写要点：**
- 仅定义语义，不使用代码变量或路径
- 字段与规则采用自然语言短句表达
- 若存在多对象依赖，分行描述
- 表格字段对齐，首字母大写

### 5.6 技能生命周期

**安装：**
1. 从技能库查询可用技能
2. 将技能链接到 Agent 的技能目录中
3. 更新 Tool.md 中的已安装技能列表

**执行：**
1. Agent 在已安装技能表中匹配用户需求
2. 读取技能的 SKILL.md 文件，按照其中的指令渐进式执行任务
3. **关键原则：执行技能 = 读取技能文件并按其指令操作，不是口头描述步骤**

**卸载：**
1. 从 Agent 的技能目录中移除
2. 更新 Tool.md，删除该技能记录

**管理原则：**
- 技能仅在技能目录中存在时才视为已安装
- 技能列表工具仅用于浏览可安装的技能库，不代表已安装状态
- 技能优先于系统工具

### 6.1 命名规则

| 层级 | 命名规则 | 示例 |

### 6.2 版本格式

使用 `major.minor.patch`，每次修改需更新元数据中的版本号。

| 变更类型 | 版本更新 |
|---------|---------|
| 重大功能变化 | `major` +1 |
| 新增内容/功能 | `minor` +1 |
| 修正/优化 | `patch` +1 |

## 七、语言与格式标准

1. 文件统一 UTF-8 编码，Markdown 格式
2. 中文主体、英文补充；元数据声明使用英文
3. Agent.md 的正文部分面向用户的内容不使用技术术语
4. 每段话 ≤ 3 行
5. 使用规范标题层级（#、##、###）
6. Role.md 中的状态机规则使用 `When→Then→Outcome` 句式
7. 各条规则独立，不嵌套；至少三条，最多七条

## 八、Project → Agent → Skill 协作流程

### 8.1 创建流程

```
1. 创建 Project
   └── 从模板复制标准文件集（Agent.md / Tool.md / Taste.md 等）
   └── 创建项目标准目录结构

2. 启动 Agent
   └── 加载所有配置文件，构建分层系统提示
   └── 注入认知系统组件
   └── 初始化记忆系统

3. 安装 Skill
   └── 从技能库选择并安装
   └── 更新 Tool.md 中的已安装技能列表

4. Agent 执行任务
   └── 接收用户消息 → 进入思维循环
   └── 匹配技能 → 读取 SKILL.md → 渐进式执行
   └── 输出结果 → 记录实践日志
```

### 8.2 协作数据流

```
用户输入
  → Agent 接收消息，进入思维循环
  → 状态检查：确认当前阶段
  → 意图理解：分析用户核心需求
  → 工具箱选择：优先匹配已安装技能
  → 执行响应：读取技能文件并按指令执行
  → 状态更新：必要时切换角色阶段
  → 输出结果给用户
  → 实践日志自动记录
  → 定期自动整理 Memory.md
```

### 8.3 三种 Agent 类型的协作方式对比

| 维度 | 角色型 Agent | 项目型 Agent | 任务型 Agent |
|------|-------------|-------------|-------------|
| 提示词层数 | 7 层 | 6 层 | 基础层 |
| 阶段管理 | 状态机驱动（Role.md 定义） | 项目内容驱动 | 无阶段 |
| 技能管理 | 可安装/卸载，.skills 目录软链接 | 内置工作流技能，按需加载 | 无独立技能 |
| 知识注入 | 全文注入 | 索引目录（Lazy Loading） | 无 |
| 记忆系统 | 完整三层记忆 | 完整三层记忆 | 无 |
| 认知系统 | 完整组件 | 完整组件 | 无 |
