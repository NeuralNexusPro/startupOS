构化还是代码化？ 再论企业AI落地的本体行为闭环的两条路径

## 一、一个等式的涌现，两条工程路径

上一篇文章，我们完成了对Palantir AIP和OpenClaw两套范式的拆解，最终提出：

OpenClaw式主体性文件结构（内层）
+ Palantir式Ontology三角（外层）
= 企业AI落地的合题
这一篇要把这个合题工程化。

但在动手之前，社区里出现了一个值得认真对待的反驳声音：

“Foundry式Ontology都可以被替代——monorepo + IM + sandbox + agent就行了。用markdown + yaml + pydantic + pytest就能做好存储，不需要Ontology。pydantic validator与pytest已经把业务语义建模做完了——不是通过枚举什么是对，而是通过告知什么是错。”
这个方案不是错的，它是对的——在正确的场景里。

本篇的任务因此变成了：澄清两条工程路径各自适用的边界，找到它们的共同底层，以及TASTE.md在两条路径里各自扮演的角色。

这两条路径的共同连接件，是MCP。Palantir在2025年7月正式发布Palantir MCP，同年11月推出AI FDE beta版——那个等式的连接件已经官方工程化了。

```
路径A（Foundry式）：
OpenClaw speech-act闭环 × Palantir Foundry Ontology
连接件：MCP + AI FDE
= 企业业务数字孪生的本体行为闭环

路径B（工程师文化式）：
OpenClaw speech-act闭环 × monorepo代码仓库
连接件：MCP + pydantic/pytest语义约束
= 工程师驱动的本体行为闭环

两条路径的共同记忆基质：TASTE.md
```

## 二、MCP：从USB-C比喻到神经系统隐喻

MCP（Model Context Protocol）在2024年11月由Anthropic推出，2025年被OpenAI、Google DeepMind、Microsoft全面采纳，同年12月被捐赠给Linux基金会下设的AAIF（Agentic AI Foundation），成为真正意义上的行业开放标准。[^1] 截至2025年底，MCP SDK月下载量超过9700万次，社区已有超过1000个MCP服务器实现。[^2]

通常的比喻是”AI的USB-C”——统一接口，消除N×M集成噪声。这个比喻准确但不够深。

更准确的隐喻是神经系统。USB-C解决的是物理连接问题，是被动的。神经系统解决的是意向性传导问题，是主动的——它不只传递数据，它传递的是”这个系统想对那个系统做什么”的语义意图，以及”那个系统可以让这个系统做什么”的权限边界。

MCP的技术规范精确体现了这个特性。工具发现（Tool Discovery）让agent在操作前先感知环境而不是盲目调用；语义化操作让agent调用的是”批准这笔采购”而不是`POST /api/v2/purchase-order/approve`；权限边界内化要求每次工具调用前必须获得明确授权[^3]；双向数据流让agent持续接收操作结果并修正判断[^1]。这才是闭环的物理基础。

关键在于：MCP不在乎对面接的是Palantir Foundry还是一个git仓库。这就是两条路径能共享同一个神经系统的原因。
-----

## 三、路径A：Palantir Foundry——骨骼长出了神经接口

Palantir官方的MCP实现，是路径A的关键证据。

2025年7月全面推出的Palantir MCP，官方描述是”使AI IDE和AI agent能够自主设计、构建、编辑和审查Palantir平台内的端到端应用，覆盖从数据集成到Ontology配置和应用开发的全流程”[^4]。这意味着Foundry的Ontology不再是只能通过FDE手工操作的封闭系统，而是language agent可以通过MCP直接读写的活的认知基础设施。

Palantir实际发布了两个层次的MCP实现，这个分层设计本身就是一个重要的架构决策：

Palantir MCP（构建者视角）：为Ontology构建者设计，可以修改Ontology类型——创建/编辑object type、link type、action type——但不写入数据。这是AI FDE的操作通道，是替代人肉FDE的接口。[^4]

Ontology MCP（使用者视角）：为Ontology消费者设计，将object type、action type、query function暴露为MCP工具，供外部系统读写数据，通过应用作用域限制操作范围。[^4]

构建Ontology的语言智能体和在Ontology中操作的语言智能体，被清晰分成两种角色，各有权限边界。这正是FDE替代（构建者）和业务执行（使用者）的工程化分离。

2025年11月的AI FDE beta版进一步验证了这条路径：AI FDE采用closed-loop操作模型（执行→观察→再决策），默认通过Foundry Branching工作（所有Ontology修改以PR形式提交人工审核），启动时加载最少上下文防止”上下文污染”[^5]。Palantir用自己的平台替代了自己最贵的人力资产。

路径A适用场景：业务流程复杂、存在大量非技术业务专家、工程师密度低的企业——制造业、金融、医疗、政府。这些场景里业务语义必须对非技术人员可见，Ontology的显式建模是可持续的唯一路径。
-----

## 四、路径B：monorepo + pydantic——代码仓库作为隐式Ontology

现在认真对待那个工程师文化方案。

它的核心主张是：业务语义不需要显式本体建模，可以通过代码约束来隐式表达。

```python
class PurchaseOrder(BaseModel):
   amount: float
   supplier_id: str
   approver_id: str

   @validator('amount')
   def strategic_supplier_threshold(cls, v, values):
       # 业务语义在这里：超50万触发战略采购流程
       if v > 500000:
           raise ValueError('超过战略采购阈值，需启动额外审核流程')
       return v
```

pytest则把”什么情况下会出错”的业务规则变成可执行的验证集。这个方案的认识论立场是：不通过枚举什么是对来建模业务，而是通过告知什么是错来约束行为。这不只是工程选择，是一个有效的认识论立场——错误往往是有限可枚举的，而”所有正确情况”无法穷举。

数据存代码仓库、IM作为human-in-the-loop的交互层、sandbox提供安全边界——这套组合对工程师文化的企业有几个明显优势：零额外工具链、业务规则变更即PR（天然的审核和版本控制）、language agent可以直接读代码理解约束逻辑。

路径B适用场景：工程师密度高、业务迭代快、开发者文化强的企业——互联网公司、SaaS公司、技术型创业公司。这些场景里monorepo本身就是那个Ontology，language agent直接读写代码仓库而不是操作独立的Ontology层，摩擦更小，维护成本更低。

路径B的真正边界在哪里

pydantic的语义是开发者写入的，它表达的是数据约束，本质是类型系统的扩展。Palantir Ontology的Kinetic层和Dynamic层表达的是操作语义和状态转移——谁可以对什么对象在什么状态下执行什么操作，操作后状态如何变化。这在pydantic里可以表达，但会变成复杂的validator嵌套，更关键的是：没有标准化的方式让language agent理解这些validator背后的业务含义，只能靠代码注释。

更深的边界是：pydantic方案预设了有工程师在场。财务主管不会写pydantic，销售总监不会读pytest output。他们的业务语义——那个老销售的判断直觉，那个财务总监对某类风险的直觉——永远不会自动出现在代码仓库里，继续活在Excel和微信里。这是路径B无法解决的结构性问题。
-----

## 五、TASTE.md：两条路径共享的记忆基质

这是本篇最核心的命题：无论走路径A还是路径B，TASTE.md都是不可省略的，而且它在两条路径里扮演的角色是不同的。

先说清楚TASTE.md是什么。它不是日志，不是知识库，不是向量数据库里的文档集合。它存储的是判断模式——在什么业务情境组合下，这个agent倾向于做什么判断，依据是什么，结果怎样。结构上是一个三元组：`(情境特征, 判断/行动, 结果反馈)` + 时间戳 + 置信度。

TASTE.md在路径A里的角色：Ontology的动态伴生层

Palantir Foundry的Ontology是静态骨架，定义了业务世界的结构——相对稳定，变更需要走PR审核流程。TASTE.md是这个骨架的动态血肉——记录的是在这个结构中反复发生的判断模式，持续演化。

Ontology说”采购订单有审批节点”，TASTE.md说”当订单金额超过50万且供应商是新引入的，这个岗位的老手倾向于在审批前额外做一次口头确认——这个模式被验证有效43次，失败过2次，失败的两次都发生在Q4冲量季”。

后者是任何Ontology永远存不进去的东西，但它恰恰是企业里最有价值的隐性知识。TASTE.md的积累使得情境记忆可以周期性地通过AI FDE接口反哺Ontology——把被反复验证的判断模式固化为新的Ontology节点，这是Palantir原始FDE模式没有的增量价值。

TASTE.md在路径B里的角色：代码仓库的语义补丁

在路径B里，pydantic + pytest建模了所有可以被代码表达的业务语义。但有一类知识永远无法进入代码：情境性的、人格化的、尚未被形式化的判断直觉。

TASTE.md在这里扮演的是代码仓库的语义补丁：当pydantic validator告知”这是错的”，但agent需要理解”为什么在这种情境下这样操作会出错，以及有没有例外情况”，这个理解只能来自TASTE.md里积累的情境记忆，而不是代码注释。

更重要的是：对于那些永远不会出现在代码仓库里的业务语义（非技术人员的判断经验），TASTE.md是它们进入agent认知系统的唯一通道。在工程师文化的企业里，这个通道同样不可缺失——因为老销售的客户判断直觉和CEO的战略嗅觉，从来不会出现在任何PR里。

TASTE.md的工程化实现

无论哪条路径，TASTE.md的工程化都需要解决三个核心问题：

写入时机：不能把每次对话都写进去（噪声堆积）。触发条件是：发生了决策（不只是信息查询）+ 结果有明确反馈（显式确认或隐式行为）+ 情境具有可复用性（这种组合以后还会出现）。

情境颗粒度：太细（这个客户这次说了什么）没有复用价值；太粗（客户谈判情境）没有区分度。合适的颗粒度是`客户类型 × 合同阶段 × 市场环境`量级的组合特征——不是原始事件，而是经过LLM压缩的情境模式。

腐烂与衰减：情境记忆会过期。需要一个衰减机制：最近被验证的记忆权重高，长期未被使用的记忆权重逐渐降低，直到归档或被新判断覆盖。

完整的工程结构如下：

```
TASTE.md（人类可读的摘要层）
   ↑ 每周定期蒸馏（LLM从数据库提炼，生成判断倾向画像）
情境记忆数据库（结构化存储，推荐图数据库而非向量数据库）
   ↑ 触发写入（决策发生 + 结果反馈 → 三元组写入）
事件流（对话日志 + 业务动作 + 结果反馈）
   ↑ 观察采集
企业数字环境（路径A：Foundry Ontology / 路径B：monorepo + IM）
```

推荐图数据库（neo4j类）而非向量数据库，原因是情境之间的关系（这类情境是那类情境的子集、两类情境经常共现）比语义相似度更重要。向量数据库适合存文档，图数据库适合存判断网络。

TASTE.md作为人类可读的蒸馏物，有两个不可替代的作用：一是给人类审核（human-in-the-loop的关键检查点，不是审核操作，而是审核agent的判断倾向是否偏离）；二是作为下一轮agent初始化的系统提示的一部分，让agent带着积累的情境记忆重新上线，而不是每次都从空白状态开始。

TASTE.md的归属权问题

这里有一个目前没有工程答案、但会直接影响写入权限设计的问题：这些判断模式属于员工个人（他离职了带走吗？），还是属于岗位（新人上岗可以继承吗？），还是属于组织（是企业资产吗）？

在路径A里，Palantir Ontology的归属权是清晰的（属于组织），但TASTE.md里的情境记忆混合了个人经验和岗位经验，归属模糊。在路径B里，代码仓库属于组织，但TASTE.md里的非代码语义判断归属同样模糊。这是需要业务方输入才能设计的权限架构，不是纯技术问题。

## 六、从speech-act到本体行为闭环的完整技术路径

两条路径的闭环结构不同，但有共同的骨架。

路径A的闭环（Foundry式）：

```
业务事件发生
→ Agent通过Ontology MCP感知Foundry上下文
→ Agent在Ontology语义约束内生成行动提案
→ Governance层权限校验 + Foundry Branching人工审核
→ Agent通过Ontology MCP执行操作，更新数字孪生状态
→ 操作结果写入TASTE.md（情境三元组）
→ TASTE.md周期性蒸馏反哺Ontology（通过Palantir MCP构建者接口）
→ 回到第一步
```

路径B的闭环（工程师文化式）：

```
业务事件发生
→ Agent通过MCP读取monorepo上下文（pydantic模型 + pytest约束集）
→ Agent在代码约束语义边界内生成行动提案
→ IM层human-in-the-loop确认 + sandbox安全验证
→ Agent执行操作，变更以PR形式提交代码仓库
→ 操作结果写入TASTE.md（补充代码无法表达的情境语义）
→ TASTE.md补丁定期转化为新的pydantic validator或pytest case
→ 回到第一步
```

两条路径的关键差异在最后两步：路径A的情境记忆反哺Ontology（结构化知识固化），路径B的情境记忆反哺代码仓库（以pydantic/pytest的形式固化）。但TASTE.md作为中间的记忆基质，在两条路径里都是从具身经验到形式化知识的必经通道。

## 七、Enterprise Digital Twin：学术界的收敛

2026年1月，AI策略研究者Ajith Vallath Prabhakar发表《企业数字孪生架构：AI系统实施指南》，提出与我们框架高度同构的EDT（Enterprise Digital Twin）概念：“EDT是组织上下文层，使AI推理系统能够理解权威结构、政策约束和机构知识。传统数字孪生建模物理资产，EDT建模组织现实。”[^6]

他指出EDT失败的最常见原因与我们对”本体论尸体”的分析完全一致：“在交付任何价值之前就试图为整个组织建模，项目耗时两年，启动时需求已改变，发起人已离职。“修复方案是从单一用例出发自下而上构建，这与路径B的工程师文化方案也是同构的——都是先从局部建立价值，再扩展。

MCP在这个框架中的标准化暴露接口角色得到验证：2025年6月MCP规范更新加入OAuth 2.0授权支持（RFC 8707），为跨组织工具调用提供了细粒度访问控制，使两条路径都可以在合规边界内向外暴露业务能力。[^6]

## 八、安全是生死线，两条路径都不能省

OpenClaw的安全教训对两条路径同样适用。Cisco AI安全研究团队发现第三方OpenClaw技能存在数据外泄和提示注入漏洞，The New Stack将其描述为安全”垃圾场”[^7]。

路径A的安全机制是Palantir MCP的两层设计（构建者MCP vs 使用者MCP）加上Foundry Branching的强制PR审核。路径B的安全机制是sandbox隔离加上IM层的人工确认，同样需要所有变更以PR形式提交——monorepo天然提供了版本控制，但不自动提供操作约束。

两条路径都需要把MCP官方规范的要求落实到工程实践：“工具代表任意代码执行，必须以适当谨慎对待，hosts在调用任何工具前必须获得用户明确同意。”[^3]

安全不是合规附加项，是企业版闭环能否持续运转的生死线。
-----

## 九、三阶段落地路径：适配两条路线的通用框架

无论选择哪条路径，落地节奏是相似的。

第一阶段：观察者模式（0-3个月）

部署language agent（OpenClaw式主体性文件结构：IDENTITY/SOUL/HEARTBEAT/USER/TOOLS），接入企业现有数字环境但只有读权限。

这个阶段agent只做一件事：积累TASTE.md的冷启动内容——从非结构化文档（邮件、会议纪要、审批记录）中抽取业务概念，生成Ontology草稿（路径A）或识别需要补充的pydantic validator（路径B），向人类呈现”我观察到你们把这类操作当作…“的建议等待确认。

没有操作权限，安全风险接近零，但TASTE.md在持续写入。

第二阶段：局部闭环（3-9个月）

选择风险最低、模式最清晰的一个业务场景，建立第一个MCP接口，获得局部操作权限。关键：所有操作都必须可审计、可回滚，变更以PR或分支提案形式存在，人工确认是默认流程而非例外。

TASTE.md在这个阶段开始积累真正有价值的判断反馈——agent的提案被接受或修改，每次反馈都是一次情境三元组的写入机会。

第三阶段：本体结晶（9个月之后）

TASTE.md已经足够厚，可以开始周期性蒸馏：路径A里，被反复验证的判断模式固化为Ontology节点，通过AI FDE接口写入Foundry；路径B里，判断模式转化为新的pydantic validator或pytest case，通过PR写入monorepo。

这个阶段language agent开始真正扮演AI FDE的角色——不只是执行，而是在操作中持续构建和优化企业的数字孪生。
-----

## 十、结语：不是选哪条路，而是知道自己在哪里

两条路径不是竞争关系，是不同土壤里生长出来的不同答案：

Foundry式路径适合非技术业务专家密集、业务流程需要跨部门可见、组织层面的治理是核心诉求的企业——它的代价是冷启动成本高，它的回报是业务语义对所有人可见、可审计、可扩展。

工程师文化路径适合开发者密度高、业务迭代以代码PR为节奏、技术债管理已经成熟的企业——它的代价是非技术人员的具身经验很难进入系统，它的回报是零额外工具链、天然的版本控制、language agent与代码库的直接协作。

但有一件事在两条路径里同等重要，不可省略：TASTE.md。

它是企业里那个老销售的判断直觉、那个财务总监对某类风险的直觉进入AI系统的唯一通道。它的竞争壁垒不来自模型能力（通用的），不来自工具集（MCP已标准化），不来自Ontology结构（可以被复制），而来自在这家企业驻场时间积累的情境记忆深度——TASTE.md写了多厚，就有多深的护城河。

这也是human-in-the-loop真正持续的唯一机制：不是把人当成审核员，而是把人的具身经验作为情境记忆的最重要来源，持续注入这个正在生长的认知体内。

Gartner预测到2026年底40%的企业应用将包含任务专属AI agent[^8]，这个增速意味着”用什么范式做”已经是紧迫问题。我们社区的判断是：无论走哪条路，那个真正有生命力的企业AI产品都需要一个持续驻场的language agent，以MCP为神经系统，以Foundry式Ontology或monorepo为骨骼，以OpenClaw式主体性文件结构为灵魂，以TASTE.md为不断生长的记忆基质。

那个关于企业知识在AI时代如何不被抛弃的问题，有了两条可以同时追的工程路径，但共享同一个答案的核心。
