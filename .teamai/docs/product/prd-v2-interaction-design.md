## 📋 执行摘要

Epic T（TASTE/SOUL 品味积累系统）的交互设计面临一个核心挑战：**如何让不可见的"品味"在交互中可感知**。

**核心设计挑战:**
1. **品味可见性问题** - 隐性品味信号本身不可见，需要设计表达方式
2. **信心度平衡** - 显示品味来源 vs 信息过载的平衡
3. **透明度与信任** - 让用户理解品味学习的过程，增强信任
4. ** Harnessing 范式交互** - 从"配置控制"转向"建立信赖"的交互模式

**设计原则:**
- **可解释但不纠缠** - 显示品味来源的案例依据，但不干扰主要任务
- **渐进透明** - 默认简洁，按需展开详情
- **主动学习信号** - 显示系统正在学习品味的状态
- **可撤回与可控** - 所有品味应用都可以纠正和撤销

## 1. SignalReader 交互设计

### 1.1 词汇选择信号 UI

由于词汇选择信号是隐性的，不需要直接的 UI 组件，而是体现为 Agent 建议风格的变化。但在调试模式或"品味洞察"面板中可以显示：

```
[品味洞察面板]

你最近的词汇选择倾向:
┌─────────────────────────────────────────┐
│  偏好词汇    频次   替代词    偏向     │
│  "可行"      8次    "有创意"   保守     │
│  "稳妥"      6次    "冒进"     谨慎     │
│  "基础"      5次    "高级"     实用     │
└─────────────────────────────────────────┘

推断: 你倾向于更保守、实用的判断风格
置信度: 85% (基于19次交互)
```

### 1.2 阻力信号与二元组消歧 UI

阻力信号不需要实时显示，但在 Agent 生成建议时，可以显示"已调整风格"的提示：

```
[Agent 建议卡片]

┌─────────────────────────────────────────┐
│  建议方案 A                              │
│                                          │
│  基于3点保守调整:                        │
│  • 降低了风险敞口                        │
│  • 选择了更成熟的实现路径                │
│  • 增加了容错机制                        │
│                                          │
│  [查看调整理由] →                        │
│  [不同意此调整，按原风格建议]            │
└─────────────────────────────────────────┘
```

### 1.3 重复模式识别 UI

当重复模式达到统计门槛时，显式通知用户：

```
[品味学习通知]

我注意到你在类似情况下更倾向于:
• 保守而非激进的方案
• 实用而非创新的风格
• 成熟而非前沿的技术栈

这是基于你过去 5 次类似选择识别的模式
[应用此模式] [忽略] [查看历史记录]
```

## 4. Meta Feedback 交互机制

### 4.1 元反馈输入 - "品味理解检查"

提供定期的"品味理解检查"入口：

```
[设置菜单]

┌─────────────────────────────────────────┐
│  • 品味理解检查 ... 新                    │
│  • 隐私设置                              │
│  • 信任管理                              │
└─────────────────────────────────────────┘

          ↓ 点击

[品味理解检查]

我对你风格的当前理解:

✅ 你偏好保守的技术决策
⚠️  但你可能偶尔需要创新的解决方案
❌ 你可能过于务实，缺少探索激情

"你对我的理解："
[非常准确] [还可以] [不太准确] [完全不对]

如果需要纠正，请告诉我在哪些方面我理解错了:
[输入框...]

[提交反馈]
```

### 4.2 修正应用的反馈循环

当用户纠正品味理解时，显示纠正将被应用：

```
[纠正确认]

你纠正了我的理解: "我偶尔需要创新"

我将调整以下建议:
• 保守方案 → 平衡方案 (保留一定创新度)
• 风险规避 → 风险评估 (不过度规避)

下次在类似情况下，我会调整建议风格。

[确认应用] [取消]
```

### 4.3 纠正应用可视化追踪

让用户看到他们的纠正已生效：

```
[我的纠正历史]

纠正 1: 创新平衡度
  时间: 2026-03-05
  内容: "我偶尔需要创新，不是一直保守"
  已应用: ✅ 3 场景
  下次应用: 技术栈选择场景

纠正 2: 沟通简洁度
  时间: 2026-03-03
  内容: "我喜欢更简洁的回复"
  已应用: ✅ 12 场景
```

```

─────────────────────

基于我们合作的历史，我可以在以下方面
```

四阶段信赖度表达：

```

  我总是需要你确认所有决策

  我可以完全自主，只在边界情况通知你
```

```
[查看我如何理解你的] [保持当前级别]
```

## 7. 关键交互流程

### 7.1 品味被纠正的交互流程

```
用户纠正品味
     ↓
显示纠正预览 ("我将调整...")
     ↓
用户确认
     ↓
系统立即应用纠正
     ↓
显示纠正已生效 (+下次应用场景)
     ↓
后续建议基于纠正调整
     ↓
用户下次看到纠正生效
```

### 7.2 品味模式固化的交互流程

```
观察积累中
     ↓
达到门槛前 (显示进度)
     ↓
达到门槛 (模式固化)
     ↓
通知用户 ("我注意到...")
     ↓
用户确认或忽略
     ↓
固化模式进入应用阶段
```

### 7.3 SOUL 身份演化流程

```
无足够数据
     ↓
引导初始设置 (SOUL 初始化向导)
     ↓
收集更多观察
     ↓
自动校准候选 (推断阶段)
     ↓
达到治理门槛 (高置信度)
     ↓
更新 SOUL → 通知用户
     ↓
用户查看演化历史
```

## 9. 约束与风险

### 交互设计约束

| 约束 | 风险 | 缓解措施 |
|------|------|---------|
| 品味可见性与信息过载 | 用户可能觉得品味信息干扰 | 默认最小化，按需展开 |
| ARIA 进度显示的复杂性 | 阶段状态难以理解 | 用简单图标和进度条 |
| MetaFeedback 入口发现性 | 用户找不到纠正入口 | 在 Header 设置中放入口 |
| 案例引用的信息量 | 5个案例可能太多 | 默认显示2个，展开更多 |

### 设计需确认的问题（与产品）

1. **品味信息默认状态** - 是否默认最小化显示？
2. **案例引用数量** - 显示多少个案例合适？（建议默认2个）
3. **MetaFeedback 频率** - 多久提示一次"品味理解检查"？
4. **身份初设向导强制性** - 是强制完成还是可跳过？

### 需要向开发团队提出的技术需求

1. **案例引用组件** - 支持动态加载和折叠展开
2. **进度状态追踪** - ARIA 各阶段的实时状态获取
3. **偏好持久化** - SOUL 和 TASTEMD 的实时同步
4. **状态通知** - 正在学习、模式固化等 Toast 通知

---

**设计结论:**

Epic T 的交互设计核心是让"不可见的品味可见化"。通过案例引用、进度追踪、分层展示等方式，用户可以感知到系统正在学习和理解他们的品味。

**关键设计决策:**
1. 品味信息默认最小化，不干扰主流程
2. 使用"案例引用式"表达，增强可解释性
3. SOUL 身份用四个维度直观表达
4. Meta Feedback 通过定期检查入口，而非强制打扰
5. Harnessing 范式用信赖度四阶段可视化
